FossaPay sends webhook events when asynchronous financial operations change state. Use them for fast updates, but retain API-based reconciliation because delivery failure and transaction failure are different conditions.

## Configure an endpoint

Add a public HTTPS endpoint from **Dashboard → Settings → Webhooks**, then securely store the generated secret. Every active webhook configured for your merchant receives applicable merchant events; event-by-event subscription filtering is not currently part of the public integration.

Your endpoint should:

- accept `POST` requests over HTTPS;
- verify the signature before trusting the event;
- return a 2xx response quickly;
- queue business processing outside the request;
- tolerate duplicate and out-of-order delivery.

## Delivery envelope

```json
{
  "eventId": "evt_mu1pstuy_63a894ef9100ec4b",
  "eventType": "deposit.completed",
  "data": {
    "transactionId": "44444444-4444-4444-8444-444444444444",
    "status": "success"
  },
  "timestamp": "2026-09-14T20:48:02.222Z"
}
```

The fields inside `data` depend on the event type. Build handlers around stable identifiers and the event's documented payload rather than assuming all event types share one transaction shape.

### Delivery headers

| Header | Meaning |
|---|---|
| `x-fossapay-Signature` | Lowercase hexadecimal HMAC-SHA256 signature |
| `X-Event-Id` | Same delivery identifier as `body.eventId` |
| `X-Event-Type` | Same event name as `body.eventType` |
| `X-Retry-Count` | Present on retry attempts |

HTTP header names are case-insensitive.

## Verify the signature

FossaPay computes HMAC-SHA256 over exactly `JSON.stringify(body.data)` using your webhook secret. It does **not** sign the complete envelope.

```javascript
import crypto from 'node:crypto';

export function verifyFossaPayWebhook(body, signature, secret) {
  if (!body || typeof body.data !== 'object' || !secret) return false;

  const expected = crypto
    .createHmac('sha256', secret)
    .update(JSON.stringify(body.data))
    .digest('hex');

  const received = String(signature || '');
  if (received.length !== expected.length) return false;

  return crypto.timingSafeEqual(
    Buffer.from(received, 'utf8'),
    Buffer.from(expected, 'utf8')
  );
}
```

<Warning>
  Preserve the parsed `data` key order when re-serializing in another language. Do not pretty-print it, sort its keys, or include `eventId`, `eventType`, or `timestamp` in the signed string.
</Warning>

## Acknowledge and process safely

```javascript
app.post('/webhooks/fossapay', async (req, res) => {
  const signature = req.get('x-fossapay-signature');
  if (!verifyFossaPayWebhook(req.body, signature, process.env.FOSSAPAY_WEBHOOK_SECRET)) {
    return res.sendStatus(401);
  }

  const accepted = await insertInboxEventIfNew({
    eventId: req.body.eventId,
    eventType: req.body.eventType,
    data: req.body.data
  });

  res.sendStatus(200);
  if (accepted) await queueWebhookEvent(req.body.eventId);
});
```

Place a unique constraint on `eventId`. Within your worker, make each financial state transition idempotent using the relevant transaction, checkout, payout, or reference identifier too.

## Event catalogue

| Area | Events | Consumer action |
|---|---|---|
| Deposits | `deposit.completed` | Reconcile the transaction and credit/notify once |
| Customer withdrawals | `withdrawal.completed`, `withdrawal.failed` | Finalize or fail the customer-funded withdrawal |
| Stablecoin transfers | `transfer.completed`, `transfer.failed` | Finalize or fail the transfer |
| Wallet movement | `wallet.balance.updated` | Refresh or reconcile the affected wallet |
| Checkouts | `checkout.completed`, `checkout.failed`, `checkout.expired`, `checkout.reversed` | Fulfill only completed checkouts; stop or reverse fulfillment for other terminal states as appropriate |
| Master payouts | `payout.completed`, `payout.failed`, `payout.reversed` | Finalize the business-funded payout |
| Bulk payouts | `payout.batch.completed`, `payout.batch.failed` | Finalize the complete batch and reconcile every recipient row |

See [Webhook Events](/api-reference/webhooks/events) for event-specific examples.

## Retries and delivery status

Any non-2xx response, network error, DNS failure, or timeout marks that delivery attempt as failed. FossaPay schedules up to five retries with exponential backoff from five minutes: approximately 5, 10, 20, 40, and 80 minutes. A background worker checks due deliveries every five minutes, so actual delivery can occur slightly later.

<Info>
  A later successful retry sets the webhook delivery to delivered. It does not alter the underlying financial transaction, which may already be successful.
</Info>

Use the dashboard webhook event log to inspect response status, error messages, retry count, and delivery state, and to retry an eligible failed event. Even with retries, your application should periodically reconcile important pending operations through their GET endpoints.

## Security and operations

- Keep webhook secrets out of source control, client applications, and logs.
- Reject an invalid or missing signature.
- Rotate a secret if it may have been exposed, then update your receiver atomically.
- Validate `eventType` against an allowlist and ignore unknown events safely.
- Store the original envelope for audit with appropriate encryption and retention controls.
- Monitor non-2xx rates and queue latency.
- Do not rely on source-IP allowlisting as a substitute for HMAC verification.

## Testing

There is no public webhook simulation endpoint. Test the handler locally with a fixture signed by the same algorithm, then perform a controlled production operation. Confirm signature verification, duplicate handling, queue processing, and reconciliation before processing regular volume.
