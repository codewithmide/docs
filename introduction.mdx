FossaPay provides payment and wallet infrastructure for businesses that need to collect, hold, and transfer funds in NGN and supported stablecoins through one server-side API.

You can create individual customers, provision customer wallets, accept bank-transfer payments, send customer- or business-funded transfers, and receive signed webhook notifications as transactions change state.

## Platform capabilities

| Capability | What it provides | Learn more |
|---|---|---|
| Customers | Merchant-scoped individual customer records used by wallet and transfer operations | [Customers](/concepts/customers) |
| NGN wallets | Dedicated bank accounts for customer collections, wallet retrieval, balances, and transaction history | [NGN wallets](/concepts/ngn-wallets) |
| Checkout Wallet | Time-limited payment instructions for one-time NGN orders and invoices | [Checkout Wallet](/guides/checkouts) |
| Stablecoin wallets | Customer and master wallets on Solana for supported USDC and USDT operations | [Stablecoin wallets](/concepts/stablecoin-wallets) |
| NGN transfers | Customer-funded transfers between FossaPay wallets or to Nigerian bank accounts | [NGN transfers](/guides/ngn-transfers) |
| Master wallet payouts | Business-funded NGN payouts from the merchant's permanent master wallet | [Master wallet payouts](/guides/payouts) |
| Webhooks | Signed notifications for deposits, withdrawals, transfers, checkouts, payouts, and wallet changes | [Webhooks](/concepts/webhooks) |

## Resource model

FossaPay integrations are organized around merchants, customers, wallets, and financial operations.

<Steps>
  <Step title="Merchant">
    Your business is the top-level owner of API keys, master wallets, customers, webhook endpoints, and all associated activity.
  </Step>
  <Step title="Customer">
    A customer represents an individual end user served by your business. Customer records are merchant-scoped.
  </Step>
  <Step title="Wallet">
    Customer wallets hold funds attributed to an individual. Master wallets hold funds owned by the business. NGN and stablecoin wallets use separate API resources.
  </Step>
  <Step title="Financial operation">
    Deposits, transfers, checkouts, and payouts create records with identifiers and statuses that you use for reconciliation.
  </Step>
  <Step title="Webhook event">
    When an asynchronous operation changes state, FossaPay delivers a signed event to each active webhook configured for the merchant.
  </Step>
</Steps>

## Understand fund ownership

Choose an API based on who owns the source funds and what the payment is intended to do.

| Source funds | Intended operation | Use |
|---|---|---|
| Customer | Receive recurring or wallet top-up payments | Customer NGN wallet |
| Customer | Send to another customer wallet under the same business | Wallet-to-wallet transfer |
| Customer | Send to an external Nigerian bank account | Customer inter-bank transfer |
| Business | Send NGN from the merchant master wallet | Master Wallet Payouts API |
| Customer | Send supported stablecoins to a blockchain address | Stablecoin transfer |
| Buyer paying an order | Make a one-time NGN bank transfer for an exact amount | Checkout Wallet |

<Warning>
  Do not use a customer wallet to represent business-owned funds or a master wallet to represent customer-owned funds. The source determines the correct API, fee treatment, and reconciliation flow.
</Warning>

## Integration lifecycle

Most integrations follow this sequence:

1. Create and verify your merchant account in the FossaPay dashboard.
2. Obtain an API key.
3. Make authenticated requests from your backend using the `x-api-key` header.
4. Store your own references together with returned FossaPay resource IDs.
5. Configure a public HTTPS webhook endpoint and securely store its secret.
6. Verify webhook signatures, acknowledge deliveries quickly, and process events idempotently.
7. Reconcile important operations with authenticated retrieval endpoints.

## Authentication and production access

Public API requests use an API key in the `x-api-key` header:

```bash
curl --request GET \
  --url https://api-production.fossapay.com/api/v1/customers \
  --header "x-api-key: $FOSSAPAY_API_KEY"
```

Keep API keys on trusted servers. Never embed them in browser code, mobile applications, public repositories, or client-visible logs.

## Asynchronous processing

Some requests return before the underlying financial operation reaches a terminal state. An accepted or processing response does not necessarily mean funds reached the beneficiary.

For asynchronous operations:

- persist the returned identifiers and your request reference;
- treat processing states as non-terminal;
- verify and deduplicate webhook deliveries using `eventId`;
- finalize your own records only from the appropriate terminal state;
- use GET endpoints to reconcile delayed or ambiguous notifications.

Webhook delivery state and transaction state are independent. For example, `fetch failed` means FossaPay could not deliver a webhook to your server; it does not mean the corresponding financial transaction failed.
